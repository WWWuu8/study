# 06 三项优化详解

## 优化 1：只针对 Shift 组合键做特殊处理

### 1. 为什么只有 Shift 特殊

普通键盘消息中：

```cpp
wParam
```

通常已经可以拿到虚拟键码。

但是：

```text
VK_SHIFT
```

不能直接告诉我们：

```text
左 Shift
还是
右 Shift
```

所以只针对 Shift 特殊处理。

### 2. 如何区分

Windows 的 `lParam` 中带有扫描码。

代码思路：

```text
VK_SHIFT
   ↓
读取 scan code
   ↓
MapVirtualKeyA
   ↓
VK_LSHIFT / VK_RSHIFT
```

### 3. 为什么不能把所有键都这样改

用户这次的要求是：

> 只针对 Shift+组合键。

因此没有把整个键盘输入系统复杂化。

原则：

```text
能不改的地方不改
只给真正有问题的键加特殊处理
```

# 优化 2：鼠标移动发送频率

## 1. 原来的问题

Windows 的 `WM_MOUSEMOVE` 可能非常频繁。

如果每一次都：

```text
WM_MOUSEMOVE
↓
send
↓
WM_MOUSEMOVE
↓
send
↓
WM_MOUSEMOVE
↓
send
```

网络里会充满大量“小移动”。

## 2. 鼠标移动的特殊性质

点击必须保留：

```text
左键 down
左键 up
```

但移动：

```text
(100,100)
(101,100)
(102,100)
(103,101)
```

中间三个位置没必要全部发送。

最重要的是：

```text
当前最新位置 = (103,101)
```

## 3. 本项目的方案

```text
WM_MOUSEMOVE
      ↓
PushMove
      ↓
g_latest_move = 最新位置
      ↓
g_move_dirty = 1
      ↓
InputThread
      ↓
每 10ms 最多发送一次
```

10ms 大约是：

```text
100 次/秒
```

所以默认值：

```cpp
#define MOUSE_MOVE_INTERVAL_MS 10
```

## 4. 为什么不是越快越好

例如 1ms：

```text
1000 次/秒
```

远程控制不一定因此更顺滑，反而可能：

```text
CPU ↑
网络包 ↑
服务器调用 ↑
延迟 ↑
```

所以优化不是：

> “让它发得越多越快。”

而是：

> “只发真正有价值的数据。”

# 优化 3：服务器处理速度

## 1. 减少无意义的大块内存操作

协议缓冲区是：

```text
BUF_SIZE = 65536
```

如果每一个很小的鼠标包都先：

```text
malloc 64KB
memset 64KB
```

实际只需要几十字节，却做了大量无意义工作。

所以发送函数尽量：

```text
直接发送 header
再直接发送 body
```

## 2. TCP_NODELAY

鼠标、键盘属于小数据、低延迟数据。

因此客户端和服务端连接都设置：

```cpp
TCP_NODELAY
```

目的是减少小包因为 Nagle 算法被等待合并造成的延迟。

## 3. 增大 socket 缓冲区

项目设置较大的：

```text
SO_RCVBUF
SO_SNDBUF
```

目的不是“越大越快”，而是减少高吞吐情况下因为缓冲区太小造成的阻塞。

## 4. 减少逐块 printf

假设一帧图片有很多块。

如果每块都：

```cpp
printf(...);
```

控制台 I/O 本身就可能成为性能瓶颈。

因此日志尽量按“帧”输出，而不是按“块”输出。

## 5. JPEG

桌面连续传输更关心：

```text
图片体积
编码速度
网络压力
```

因此当前版本使用 JPEG。

# 最终优化思维

不要记成三个孤立的技巧。

应该记成：

```text
数据很多
   ↓
先判断哪些数据真的重要
   ↓
鼠标中间位置可以丢
   ↓
小包不能因为线程竞争而交错
   ↓
大图片不能疯狂 printf
   ↓
大图片使用 JPEG + 分块
   ↓
服务器处理速度提升
```
