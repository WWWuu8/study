# 05 屏幕截图与分块传输

## 1. 先不要想 JPEG

先理解最简单的目标：

> 我想把服务器屏幕上的一张图送到客户端。

所以首先需要：

```text
屏幕 -> 内存里的图片
```

Windows 中用 DC 描述绘图设备。

## 2. GetDC(NULL)

服务器：

```cpp
HDC screenDC = GetDC(NULL);
```

这里的 NULL 表示拿整个屏幕的 DC。

可以把 DC 暂时理解成：

> “操作屏幕像素的画布接口。”

## 3. BitBlt

```cpp
BitBlt(..., screenDC, ..., SRCCOPY | CAPTUREBLT);
```

意思可以简单理解成：

```text
屏幕
 |
 | 复制像素
 v
CImage
```

## 4. CImage 是什么

可以把它理解成：

> 一个方便操作图片的 Windows/ATL 图片对象。

它可以保存、加载图片。

## 5. Save 到 IStream

图片不能直接当普通 C 字符串处理。

JPEG 是二进制数据。

所以：

```text
CImage
  ↓
IStream
  ↓
内存中的 JPEG
```

## 6. 24 字节分块头

本项目定义：

```text
6 个 uint32_t
```

也就是：

```text
6 × 4 = 24 字节
```

内容：

```text
[0] totalSize
[1] chunkIndex
[2] chunkCount
[3] width
[4] height
[5] format
```

其中：

```text
format = 1
```

表示 JPEG。

## 7. chunkIndex 为什么重要

假设一张图片被切成：

```text
chunkCount = 4
```

那么：

```text
chunkIndex = 0
chunkIndex = 1
chunkIndex = 2
chunkIndex = 3
```

客户端可以计算：

```text
offset = chunkIndex * CHUNK_DATA_SIZE
```

然后放回：

```cpp
frameBuf + offset
```

## 8. 为什么不能只用“收到顺序”

虽然当前 TCP 本身保证字节有序，但协议设计中保留 index 很有价值：

```text
它明确告诉接收方：
“这块数据属于完整图片的哪个位置。”
```

以后如果改成其他传输方式，也更容易扩展。

## 9. 客户端收到完整图片后

流程：

```text
chunk 0
chunk 1
chunk 2
...
chunk N
   ↓
received == chunkCount
   ↓
DisplayFrame
```

然后才：

```text
CMD_SCREEN
```

请求下一帧。

## 10. 这就是为什么画面不会无限积压

错误思路：

```text
客户端
CMD_SCREEN
CMD_SCREEN
CMD_SCREEN
CMD_SCREEN
CMD_SCREEN
...
```

正确思路：

```text
CMD_SCREEN
   ↓
完整一帧
   ↓
显示
   ↓
CMD_SCREEN
   ↓
完整一帧
```

这就是本项目的简单流控。
